# depgraph

Инструмент командной строки для визуализации графа зависимостей пакетов
NuGet (.NET). Написан на Python 3 только на стандартной библиотеке: менеджеры
пакетов и сторонние библиотеки для получения зависимостей не используются.

## 1. Общее описание

Параметры работы задаются опциями командной строки. Инструмент:

* получает зависимости заданной версии пакета из репозитория NuGet по
  протоколу V3 (`index.json`) стандартным `urllib`, манифест пакета
  (`.nuspec`) разбирает стандартным `xml.etree`;
* строит граф зависимостей с учётом транзитивности рекурсивным обходом в
  глубину (DFS) с ограничением глубины (`--max-depth`), исключением пакетов
  по подстроке (`--filter`) и обработкой циклов;
* выводит граф на экран в виде описания на языке диаграмм **PlantUML**, а по
  параметру `--ascii-tree` - ещё и в виде ASCII-дерева;
* в тестовом режиме (`--repo-mode test`) читает граф из файла, где пакеты
  названы заглавными латинскими буквами, и умеет выводить обратные
  зависимости пакета (`--reverse`).

Требуется Python 3.10 или новее.

## 2. Описание функций и настроек

### Опции командной строки

| Опция               | Обяз.        | Описание                                                    |
|---------------------|--------------|-------------------------------------------------------------|
| `--package`         | да           | Имя анализируемого пакета                                   |
| `--repo`            | да           | URL-адрес репозитория NuGet или путь к файлу тестового репозитория |
| `--repo-mode`       | нет          | Режим работы с репозиторием: `remote` (по умолчанию) или `test` |
| `--package-version` | в `remote`   | Версия пакета                                               |
| `--ascii-tree`      | нет          | Дополнительно вывести зависимости в формате ASCII-дерева    |
| `--max-depth`       | нет          | Максимальная глубина анализа, 0..500 (по умолчанию 3)       |
| `--filter`          | нет          | Не учитывать пакеты, имя которых содержит подстроку         |
| `--reverse`         | нет          | Вывести обратные зависимости пакета (только `--repo-mode test`) |

Режимы `--repo-mode`:

* `remote` - `--repo` является URL-адресом сервиса NuGet V3
  (например, `https://api.nuget.org/v3/index.json`);
* `test` - `--repo` является путём к файлу тестового репозитория.

### Обработка ошибок

При неверном параметре печатается сообщение `Ошибка: ...` в поток ошибок,
код завершения процесса равен 2. Проверяются: наличие имени пакета и его
формат (идентификатор NuGet либо заглавные латинские буквы в тестовом
режиме), формат URL, существование файла тестового репозитория, допустимое
значение режима, формат версии, целочисленность и диапазон глубины, отсутствие
пробельных символов в подстроке фильтрации, неизвестные опции.

### Как собираются зависимости (этап 2)

1. Из `--repo` (адрес службы `index.json`) берётся адрес ресурса
   `PackageBaseAddress`.
2. Версия приводится к нормализованному виду (`1.0` -> `1.0.0`), имя и
   версия переводятся в нижний регистр, скачивается
   `{base}/{id}/{version}/{id}.nuspec`.
3. В манифесте зависимости разбиты на группы `group` по целевым платформам.
   NuGet выбирает для проекта одну группу под платформу проекта. Платформа не
   входит в параметры инструмента, поэтому берётся группа **самой новой
   платформы пакета**: .NET 5+ (`net6.0`, `net8.0`, ...) новее .NET Core,
   затем идут .NET Standard и .NET Framework; платформы с суффиксом
   (`net8.0-android`) и неизвестные уступают обычным. Зависимости без группы
   считаются относящимися к любой платформе. Так результат совпадает с
   `dotnet list package` для проекта на новейшей платформе пакета (объединять
   все группы нельзя: устаревшие группы `netstandard1.x` тянут десятки лишних
   пакетов).
4. Диапазон версий зависимости разрешается в конкретную версию так же, как
   это делает NuGet: берётся наименьшая версия репозитория, подходящая под
   диапазон (`NuGetRepository.resolve_version`). Пререлизы учитываются,
   только если нижняя граница диапазона - пререлиз.

Ошибки получения данных (нет сети, пакет или версия не найдены, ответ
службы не JSON, повреждённый `.nuspec`) печатаются как `Ошибка: ...`, код
завершения 1.

### Построение графа (этап 3)

Граф строит `DependencyWalker` (`src/depgraph/graph.py`) рекурсивной
функцией `_visit` - обходом в глубину:

* корень имеет глубину 0, его зависимости - глубину 1 и т. д.; вершина на
  предельной глубине не раскрывается (в выводе помечается
  «достигнута максимальная глубина»);
* вершина раскрывается повторно, если до неё дошли более коротким путём, - из-за
  порядка обхода иначе пропадали бы зависимости, укладывающиеся в глубину;
* пакет, чьё имя содержит подстроку `--filter`, не попадает в граф, его
  зависимости через него не обходятся (сравнение без учёта регистра, как и
  сами имена NuGet); если подстрока содержится в имени корневого пакета,
  выводится ошибка;
* зависимость от пакета, лежащего на текущем пути обхода, - циклическая;
  ребро добавляется в граф, но по нему обход не продолжается, а в конце
  вывода печатается список таких рёбер;
* одинаковые пакеты (без учёта регистра) - одна вершина; версия вершины -
  первая, встреченная при обходе (NuGet выбирает наибольшую из нижних границ
  диапазонов, поэтому в «ромбах» версии могут отличаться от выбора NuGet).

Вывод: заголовок (число вершин и рёбер, параметры), затем строка
`пакет -> зависимости` на каждую вершину в порядке обхода и список циклов.

### Обратные зависимости (этап 4, `--reverse`)

Обратные зависимости пакета - это пакеты, которые зависят от него. Режим
включается опцией `--reverse` и доступен только для тестового репозитория:
реальный NuGet не отдаёт списка пакетов, зависящих от заданного, а в файле
описан весь репозиторий.

Из зависимостей всех пакетов файла строится обращённый граф (для каждого
пакета - список пакетов, которые от него зависят), после чего **тот же
обход DFS** (`build_graph`), что и на этапе 3, запускается от заданного
пакета. Поэтому `--max-depth`, `--filter` и обработка циклов работают так же.

Вывод: перечень пакетов, зависящих от заданного (напрямую и через другие
пакеты), и строки вида `X <- Y` («пакет Y зависит от пакета X»).

```console
$ ./run.sh --package D --repo tests/data/simple.txt --repo-mode test --reverse
Обратные зависимости пакета D (максимальная глубина 3, фильтр: нет)
Зависят от него (3): B, A, C
Запись «X <- Y»: пакет Y зависит от пакета X
D <- B, C
B <- A
A (от него никто не зависит)
C <- A
```

### Визуализация (этап 5)

Стандартный вывод в обычном режиме - описание графа на PlantUML. Корневой
пакет закрашен голубым, пакеты, не раскрытые из-за предельной глубины, -
жёлтым, ребро, замыкающее цикл, - красная пунктирная стрелка с подписью
«цикл». Описание можно передать в PlantUML для получения картинки:

```sh
./run.sh --package Serilog.Sinks.File --repo https://api.nuget.org/v3/index.json \
         --package-version 5.0.0 > graph.puml
java -jar plantuml.jar -tpng graph.puml
```

С параметром `--ascii-tree` после диаграммы печатается дерево. Повторяющаяся
вершина раскрывается только при первом появлении (дальше - `(см. выше)`),
возврат на вершину текущего пути помечается `(цикл)`, вершина, не раскрытая
из-за глубины, - `...`. Для `--reverse` дерево показывает пакеты, зависящие
от заданного.

```text
A
|-- B
|   `-- D
`-- C
    |-- D (см. выше)
    `-- E
```

### Тестовый репозиторий (`--repo-mode test`)

Файл содержит по строке на пакет: `ИМЯ: зависимость зависимость ...`.
Имена - заглавные латинские буквы, `#` начинает комментарий, пакет, который
упомянут только как зависимость, считается пакетом без зависимостей.

```text
# Ромб без циклов
A: B C
B: D
C: D E
```

Версия в тестовом режиме не используется. Примеры файлов - в `tests/data`.
Ошибки формата (нет двоеточия, недопустимое имя, повторное описание пакета)
сообщаются с номером строки.

### Модули

* `src/depgraph/config.py` - разбор и проверка параметров (`parse_config`);
* `src/depgraph/cli.py` - точка входа (`main`), выбор репозитория, вывод;
* `src/depgraph/graph.py` - граф и обход DFS (`Graph`, `DependencyWalker`,
  `build_graph`);
* `src/depgraph/model.py` - пакет (`Package`);
* `src/depgraph/reverse.py` - обращение графа репозитория
  (`reverse_neighbors`);
* `src/depgraph/render.py` - вывод: PlantUML, ASCII-дерево, список обратных
  зависимостей;
* `src/depgraph/testrepo.py` - тестовый репозиторий из файла
  (`FileRepository`);
* `src/depgraph/nuget.py` - клиент NuGet V3 (`NuGetRepository`);
* `src/depgraph/nuspec.py` - разбор `.nuspec` (`parse_dependencies`);
* `src/depgraph/versions.py` - версии и диапазоны версий NuGet;
* `src/depgraph/errors.py` - исключения репозитория.

## 3. Сборка, запуск и тесты

Сборка не требуется. Запуск:

```sh
./run.sh --package Serilog --repo https://api.nuget.org/v3/index.json \
         --package-version 3.1.1
make run ARGS="--package A --repo tests/data/simple.txt --repo-mode test"
```

Тесты (стандартный `unittest`) и проверка стиля (`flake8`):

```sh
make test
make lint
```

## 4. Примеры использования

Реальный пакет, диаграмма PlantUML и ASCII-дерево:

```console
$ ./run.sh --package Serilog.Sinks.File \
           --repo https://api.nuget.org/v3/index.json --package-version 5.0.0 \
           --ascii-tree
@startuml
title Граф зависимостей пакета Serilog.Sinks.File 5.0.0
skinparam shadowing false
rectangle "Serilog.Sinks.File 5.0.0" as n0 #LightBlue
rectangle "Serilog 2.10.0" as n1
n0 --> n1
@enduml

ASCII-дерево зависимостей:
Serilog.Sinks.File 5.0.0
`-- Serilog 2.10.0
```

Тестовый репозиторий с циклом:

```console
$ ./run.sh --package A --repo tests/data/cycle.txt --repo-mode test \
           --max-depth 10 --ascii-tree
@startuml
title Граф зависимостей пакета A
skinparam shadowing false
rectangle "A" as n0 #LightBlue
rectangle "B" as n1
rectangle "C" as n2
rectangle "D" as n3
n0 --> n1
n1 --> n2
n2 -[#red,dashed]-> n0 : цикл
n2 --> n3
@enduml

ASCII-дерево зависимостей:
A
`-- B
    `-- C
        |-- A (цикл)
        `-- D
```

Ошибка:

```console
$ ./run.sh --package NoSuchPackageXyz \
           --repo https://api.nuget.org/v3/index.json --package-version 1.0.0
Ошибка: пакет 'NoSuchPackageXyz' версии 1.0.0 не найден в репозитории
```

## 5. Сравнение со штатными инструментами NuGet

Результат инструмента сверялся с `dotnet list package --include-transitive`
и `dotnet nuget why` (проект на `net8.0` с одним `PackageReference`). Для
Serilog.Sinks.File 5.0.0, Microsoft.Extensions.Logging 8.0.0 и
Microsoft.EntityFrameworkCore 8.0.0 наборы пакетов, версии и рёбра графа
совпали. Возможные расхождения:

* платформа: штатные средства берут группу зависимостей под платформу
  проекта, инструмент - группу самой новой платформы пакета; для проекта
  на другой платформе (например, `netstandard2.0`) состав пакетов будет другим;
* версии: инструмент берёт версию вершины, встретившуюся при обходе первой,
  NuGet - наибольшую из нижних границ диапазонов по всему графу, поэтому
  в графах с «ромбами» версии могут различаться;
* глубина (`--max-depth`) и фильтр (`--filter`) в штатных средствах
  отсутствуют;
* штатные средства показывают плоский список или пути до пакета, а не граф.
